# 2026-10-13 gpt-6.1-sol 首字延迟：new-api 28s vs sub2api 4s

日期：2026-10-13  
范围：new-api 渠道 `sub-gpt-0.25` → 同机 sub2api `http://sub2api:8080`  
结论先行：多出来的 ~24.5s 发生在 sub2api **开始处理之前**，根因是 **user 1 用户并发槽 = 5 已占满**，不是 DNS、不是域名解析、不是账号 13 本地 `concurrency=10`，也不是 OpenAI 把 Plus 硬限到 2 路。

---

## 1. 现象

同一条 `gpt-6.1-sol` 请求：

| 观测点 | 首字 |
| --- | --- |
| sub2api `usage_logs.first_token_ms` | **4261ms** |
| new-api FRT | **28578ms** |

差额约 **24.3s**。用户直观感觉是「sub 里已经 4s 出字，接到 new-api 后变成 28s」。

匹配请求：

- new-api request id：`202610130849337121461258268d9d6IEelcEYs`
- new-api 用户 / token / 渠道：`y996108601` / token 11 / channel 69 `sub-gpt-0.25`
- 渠道 Base URL 当时已是容器内网 `http://sub2api:8080`（client IP `172.18.0.5`）
- sub2api usage_log：`141917`
- session：`01a13452-c215-7181-8945-7604f7d1b00b`
- 账号：**13**（oauth）
- api_key：**14**（`gpt-0.25`，group 2，user 1）
- inbound：`/v1/responses`，`stream=true`，`reasoning_effort=high`

同 session 前后几轮 new-api FRT 只比 sub 多约 150ms。只有这一轮被空等抬上去。

## 2. 墙钟时间线

`usage_logs.created_at` 是**结束时间**，开始时间用 `created_at - duration_ms`。

| 时间 (Asia/Shanghai) | 事件 |
| --- | --- |
| 16:49:33.57 | new-api GIN 接到请求 |
| 16:49:34 左右 | new-api 配额检查通过，开始等上游 HTTP 响应 |
| 16:49:57.03 | 同用户另一条账号 13 请求 `141915` 结束，释放用户槽 |
| 16:49:58.18 | `141917` 才开始计 `duration_ms`（sub 真正开干） |
| 16:50:02.4 | 上游首字，sub `first_token_ms=4261` |
| 16:50:07.14 | 本轮结束，`duration_ms=8962` |

new-api FRT 28578ms：`16:49:33.57 + 28.578s ≈ 16:50:02.1`，和 sub 首字墙钟对齐。  
**多出来的时间全部在 sub 开始处理之前**，转发 SSE 本身没有再吞 20 多秒。

## 3. 根因：用户并发槽 = 5，不是账号 13 只有 2 路

16:49:34 时刻，**同一把钥匙** `api_key 14 / user 1` 已经有 5 条在途：

| usage_log | 账号 | 模型 | 开始 | 结束 |
| --- | --- | --- | --- | --- |
| 141920 | **13** | gpt-6.1-sol high | 16:47:15 | 16:50:48 |
| 141916 | 86 | grok-4.6 | 16:48:11 | 16:50:02 |
| 141921 | 78 | gpt-6.1-sol xhigh | 16:48:57 | 16:50:51 |
| 141923 | 86 | grok-4.6 | 16:49:09 | 16:50:57 |
| 141915 | **13** | gpt-6.1-sol medium | 16:49:32 | 16:49:57 |

配置：

- `users.concurrency`（user 1）= **5**
- config `default.user_concurrency` = 5
- 账号 13 `concurrency` / `load_factor` = **10 / 10**
- 账号 13 该时段 overlap 最高只有 **3**（近 3 小时能到 5）

sub2api OpenAI `/v1/responses` 热路径是：

1. `AcquireUserSlotWithWait`（用户槽，满则排队，默认最长 30s）
2. 选账号 + 必要时 `AcquireAccountSlotWithWaitTimeout`
3. 才转发上游，开始写 `usage_logs.duration_ms`

第 6 路就是 `141917`。用户槽满了就排，`141915` 结束才轮到它。  
所以账号 13「看起来只有 2 路」，是因为另外 3 个用户槽在 **grok×2 + 账号 78 的 xhigh** 上。13 自己还空着 8 个本地槽。

这 **不是**：

- OpenAI Plus 把账号 13 硬限到 2 路（本地 cap=10，当时只用了 2）
- 账号 13 Redis 槽满
- new-api 渠道并发
- 域名解析 / TLS（已经走 `http://sub2api:8080`）

## 4. 粘滞：决定「等到之后还是 13」，不是这 24s 的原因

当时设置：

- `session_binding_enabled=false`（主要影响 Claude 路径）
- `openai_advanced_scheduler_enabled=false`
- `LOAD_BALANCE_STRATEGY=round-robin`
- `openai_ttft_mode=semantic`

OpenAI 网关仍有 **session-hash 粘滞**。session `01a13452-...`：

- 16:15–16:18：前 3 轮在账号 **78**
- 16:18:25 切到账号 **13** 后，后续 high 轮一直钉在 13（含本轮）

当时其它 oauth 账号：

- 账号 27：5h 额度 100%，`rate_limited_at` 15:55 → `reset` 18:03，不可调度
- 账号 78：并没有挂，16:48:57–16:50:51 正在跑一条 xhigh，首字 51.6s

粘滞解释的是「用户槽腾出来以后为什么还是 13」。  
排队解释的是「为什么 13 看起来只有 2 路、new-api 首字被抬到 28s」。

Sticky 满槽时的行为（先进调度器，当前开关是关的，但代码路径仍在）：

- 粘住账号 Redis 槽抢不到：若 sticky-escape 开启，会因 `concurrency_full` 逃逸换号
- 否则返回 `WaitPlan`（默认 sticky wait 45s / max waiting 3），继续等**同一账号**
- 本次等的是 **user slot**，还没走到账号 WaitPlan

## 5. SSE 头能不能在排队时先冲下去？

### 5.1 sub2api：会冲，但冲的是注释行，而且要等第一个 ping tick

`backend/internal/handler/gateway_helper.go`：

- OpenAI 网关：`NewConcurrencyHelper(..., SSEPingFormatComment, pingInterval)`
- `SSEPingFormatComment = ":\n\n"`
- `pingInterval <= 0` 时默认 **10s**
- `waitForSlotWithPingTimeout` 在排队期间：
  - 第一次 ping 才写 `Content-Type: text/event-stream` 等头，并 `Flush`
  - 之后每隔 pingInterval 再写一行 `:` 注释

这条等了 24s，理论上 10s、20s 各有一次注释心跳。  
compact 路径另有 `StartOpenAICompactSSEKeepalive`，同样是注释行，且明确「心跳字节不构成语义响应」。

### 5.2 new-api：注释行不算首字

`relay/helper/stream_scanner.go`：

- 扫描上游 SSE 行
- 长度 `< 6` 直接 `continue`
- 不是 `data:` / `[DONE]` 直接 `continue`
- 只有有效 `data:` 才 `SetFirstResponseTime()`

因此：

- 排队时冲 `:` 能防反向代理空闲超时
- **不能**把 new-api FRT 从 28s 降下来
- sub `openai_ttft_mode=semantic` 同样不算注释，所以 4261ms 是诚实的上游首字

另外：new-api 的 `StreamScannerHandler` 要等上游 HTTP 响应开始后才工作。若 10s 内还没 ping，new-api 会一直堵在读响应头；即便 10s 时冲了注释，FRT 仍等到第一条 `data:`。

### 5.3 不建议用假 `data:` 刷 FRT

若在拿到用户槽之前发 `response.created` 这类 `data:` 事件：

- new-api FRT 会立刻掉下来
- 数字是假的，语义首字被污染
- sub 自己的 semantic TTFT 仍应保持诚实

要观测排队，应单独记 wait（代码里已有 `acquireQueueWaitMs` 一类指标名），不要把它算进 first token。

## 6. 处理建议

按优先级：

1. **治本**：`gpt-0.25` 这把钥匙会同时跑 grok + 多路 gpt，user 1 `concurrency=5` 太紧。提到 8–10，或把 grok / gpt 拆到不同用户/钥匙，避免互相占槽。
2. **满槽策略**：现在默默排最多 30s。若不想让 new-api 首字被空等抬上去，可改为立刻 429 / `timeout waiting for user concurrency slot`，让客户端重试或换通道。
3. **保活（可选）**：把 `Concurrency.PingInterval` 调到 1–2s，并在进入排队时立刻 `WriteHeader` + Flush。只防空闲超时，**不降 FRT**。
4. **不要**为了 FRT 好看提前打假 `data:`。
5. **不必**再改 new-api Base URL，**不必**为这次重启 new-api。容器网络 `http://sub2api:8080` 已经绕开域名解析，不是本轮 24s 的来源。

## 7. 排查时用过的判定式

假设 `created_at` 为结束时间，请求在时刻 `T` 在途：

```sql
start_at = created_at - duration_ms * interval '1 ms'
in_flight(T) := start_at <= T AND created_at > T
```

16:49:34 对 `user_id=1` 应用上式，得到正好 5 条；`141917` 的 start 落在 `141915` 结束之后约 1s。

账号 13 同期 overlap 只有 2，排除「13 的 10 路本地槽满了」。
